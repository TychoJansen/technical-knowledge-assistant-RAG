# Data preparation: architectural choices

## prepare.py

- **Download once, then work offline.** Reproducible and fast; only this module knows the external source.
- **Idempotent steps.** Existing files are skipped. `--force` re-downloads the data, `--resplit` remakes the split,
  and neither touches the other, so a re-download never changes the split.
- **Corpus as Parquet, queries as JSON Lines.** Parquet is compact and lets you read single columns; JSON Lines fits
  the nested nuggets.
- **Corpus chunks kept as provided.** The relevance judgments refer to these exact chunks.
- **Question = title + body.** That is how a user asks; title and body are also stored for query variants.
- **Question-level relevance = union over nuggets.** The per-nugget judgments are kept as well.
- **Fixed, seeded dev/test split (60/143), stratified by language.** The test set stays held out, and both splits have
  the same mix of JS and Python questions.
- **Sanity checks on every run** (`stats.json`), so a broken or changed download is noticed straight away.

## data.py

- **The only place that loads the data files**, so it is clear which code touches evaluation data.
- **One shared definition of a question's language**, used by the split and the evaluation.
- **Plain functions and plain types**, with no caching: the data is small and loaded once per command.

## Findings and their impact

| Finding | Impact on results | Used in the code |
|---|---|---|
| 49,514 chunks from 10 repos; LangChain is only a third (llama_index 28%, transformers 27%) | Many near-topic distractors from neighbouring libraries compete in retrieval | All chunks are indexed |
| Chunks are large (median 3.9k, p95 9.0k characters; a few up to 21.8k) and do not overlap | Only a few chunks fit in a prompt; short-input embedding models truncate them; an explanation can be split over two chunks | Top 4 chunks, each cut to 2,000 characters. Adding neighbouring chunks: not yet |
| Noise: 5.5% of chunks are under 50 characters, 13% are exact duplicates, and `BUILD`, `.svg` and `.map` files have no relevant chunks | Duplicates and boilerplate take up top-k slots; filtering them is cheap and costs almost no recall | Not yet: the baseline stays unfiltered. Duplicates are excluded from the abstention test |
| Only 3.1% of chunks (1,547) are ever relevant: 51% come from langchain, 24% from langchainjs, 2% from transformers | Docs, notebooks and `.ts` are over-represented among relevant chunks. Still, 25% of relevant chunks lie outside the two LangChain repos, so the search space should not be narrowed | Every question is searched against the full corpus |
| Notebooks are stored as raw JSON (cell metadata, escaped strings) but make up 27% of the relevant chunks | The JSON noise hurts both BM25 and embeddings on a large share of the evidence | Not yet: notebooks are indexed as raw JSON |
| A few overview chunks (e.g. `concepts.mdx`, the RAG tutorial) are relevant for 8-9 questions each | A retriever that favours general overview pages scores well on many questions at once | — |
| 110 Python questions have relevant chunks in langchainjs | Filtering by question language would lose recall | No language filter |
| 203 questions, long and noisy (median 1.3k characters, up to 13.6k, with pasted code and logs) | Hurts lexical retrieval: pasted logs match unrelated files | `--query-mode` (shorter search query); tested, did not help |
| ~68 of 49.5k chunks are judged per question; the rest counts as not relevant | Recall is a lower bound; a new retriever can be under-scored, so report unjudged@k next to recall | `Unj@10` reported next to recall |
| ~3 nuggets and ~11 relevant chunks per question; nuggets are generated by GPT-4o | Nugget-based scoring fits RAG, but the nuggets are not human-verified | `Cov@20` as the primary metric; nugget recall for answers |
| 1,842 (question, chunk) pairs are relevant for one nugget and not relevant for another | Question-level relevance is generous; per-nugget coverage is stricter | Coverage uses the per-nugget judgments; the abstention test excludes chunks relevant to any nugget |
| 191 Python vs 12 JS questions (4 JS in dev, 8 in test) | Per-language results are not interpretable | Split stratified by language; per-language metrics reported for completeness |
| Dev has 60 questions; one question ≈ 1.7 percentage points | Differences of 1-2 points are noise | Runs are compared per question with 95% bootstrap intervals (`rag eval compare`) |
| Questions are from 2023-2024, while the corpus is a snapshot from October 2024 | Reference answers may use deprecated APIs; score on nuggets (facts), not on matching the reference answer | Answers scored on nuggets, not on matching the reference answer |
| `stats.json`: 0 relevant `doc_id`s missing from the corpus | The data is consistent: every relevant chunk can be retrieved | Checked on every `rag prepare` |
| Dev and test are similar, but not identical: dev questions are longer (median 1,426 vs 1,226 characters) and have slightly fewer nuggets (2.98 vs 3.22) | Dev numbers need not transfer exactly to test | Choices are made on dev only; test is run once with the frozen configuration |
